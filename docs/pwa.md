# Alfa E-commerce PWA

This document describes the production PWA layer added to the Alfa E-commerce
frontend. It is intentionally self-contained: no backend API was changed.

## Temporary feature switch (kill switch)

PWA support is controlled by one build-time variable:

```bash
NEXT_PUBLIC_ENABLE_PWA=true
```

When the variable is absent, empty, or `false`, the PWA is disabled. The
default is **disabled**.

While disabled:

- No service worker is registered and no update checks run.
- Any existing Alfa service-worker registration is unregistered on the next
  page load. Cache Storage and all other browser data are preserved.
- Install prompts, update prompts, the offline banner, and the mobile-menu
  install entry are not rendered.
- The web app manifest, Apple web-app metadata, iOS launch images, and the
  pre-hydration `beforeinstallprompt` capture are omitted from the page.
- The service worker file, manifest, icons, caching code, install UI, hooks,
  utilities, tests, and dependencies remain in the repository unchanged.

The switch is read at build time, so a rebuild/restart is required after
changing it. No files need to be restored and no packages need to be
reinstalled.

### Disable the PWA

1. Set `NEXT_PUBLIC_ENABLE_PWA=false` (or remove the variable).
2. Rebuild and restart the frontend (`npm run build && npm run start` in
   production, or restart `npm run dev` locally).
3. Open the site. The app unregisters its existing service worker and leaves
   existing caches intact.

### Reactivate the PWA

1. Set `NEXT_PUBLIC_ENABLE_PWA=true`.
2. Rebuild and restart the frontend.
3. No other change is required. The existing service worker, manifest,
   install UI, offline support, and update flow become active again.

## What is implemented

- `public/manifest.webmanifest` with standalone display, app identity, theme,
  192/512 icons, maskable icons, Apple touch icon, and shortcuts.
- A hand-written service worker (`public/sw.js`) generated from
  `scripts/sw-template.js` at build time. It is not a third-party Workbox
  runtime dependency. The generated file is git-ignored and reproduced by
  `prebuild`; never commit or deploy a locally generated copy.
- Precaching of the offline shell, manifest, app icons, and logo.
- Runtime caching policies:
  - `_next/static/*` and fonts: cache first (immutable, hashed URLs).
  - Public pages (`/`, product/category/search pages, About): network first
    with cached HTML fallback and a dedicated offline page.
  - Public API GETs (`/api/public/*` only): fresh cache with TTL, then network,
    then stale cache. Product data is fresh for 5 minutes; categories 30
    minutes; reference data such as governorates/contact 24 hours.
  - Images: cache first with background revalidation, capped at 120 entries.
  - `/api/auth/*`, `/api/users/*`, `/api/shopCarts/*`, `/api/orders/*`,
    `/api/return-orders/*`, `/api/admin/*`, and all POST/PUT/DELETE requests:
    network only.
- Requests carrying an `Authorization` header are never written to Cache
  Storage.
- Cache versioning is derived from a content hash of the frontend source and
  build inputs, so a deployment changes the service worker and old caches are
  removed during activation.
- User-approved updates: a new service worker waits until the user chooses
  "Update now". Checkout operations block update activation and therefore the
  update-triggered reload.
- Cross-tab coordination:
  - A checkout holds a shared Web Lock (`alfa-pwa-checkout`) for its duration.
  - Update activation requests an exclusive `ifAvailable` lock, so it cannot
    start while any tab is checking out. A tab crash or close releases the
    browser lock automatically.
  - Versioned per-tab localStorage leases and a heartbeat provide the fallback
    when Web Locks is unavailable. Leases expire after 30 seconds, so abandoned
    tabs cannot block updates indefinitely.
  - BroadcastChannel coordinates checkout state and update notifications; when
    it is unavailable the same messages use a localStorage event bus.
  - Other tabs are notified when an update is available and after activation,
    and show a "Refresh" prompt instead of reloading silently.
- Custom install experience:
  - Captures `beforeinstallprompt` before hydration and exposes a custom
    install dialog.
  - Provides iOS Safari "Add to Home Screen" instructions.
  - Detects standalone mode/`appinstalled` and hides unnecessary prompts.
  - Remembers dismissal for 14 days.
  - Adds an "Install app" entry to the existing mobile menu.
- iOS launch images for the common iPhone/iPad logical viewport sizes,
  generated by `scripts/generate-pwa-assets.ps1`.
- Offline banner and recovery state, with cached-page navigation and a
  standalone offline fallback at `/offline.html` (and the `/offline` route).
- Safe logout: page and public-API caches are cleared on logout/login and when
  an expired session is detected by `RequireAuth`, while static assets and
  public images remain available.
- Catalog invalidation after an admin mutation clears page, public-API, and
  image caches so changed product/slider imagery is not pinned for 24 hours.
- Server reachability probes bypass Cache Storage (`__alfa_health=1`), so a
  cached public response cannot hide a real API outage.
- Service-worker activation is refused while the browser is offline or while
  checkout/order placement is in flight.

## Build and deployment

See [`docs/pwa-deployment.md`](./pwa-deployment.md) for the production
checklist, header verification commands, CDN purge steps, and real-device
smoke-test checklist.

`sharp` was added as a production dependency because Next.js uses it for
image optimization in production; without it Next falls back to a slower
optimizer and warns at startup.

Requirements:

- Node.js **20.9+** (Next.js 16 requirement).
- HTTPS in production. The service worker only registers in secure contexts
  (localhost is treated as secure for development).
- Run the normal build command. `prebuild` regenerates `public/sw.js`:

```bash
npm ci
npm run build
npm run start
```

Required environment variables:

```bash
NEXT_PUBLIC_ENABLE_PWA=true
NEXT_PUBLIC_API_BASE_URL=https://api.example.com
NEXT_PUBLIC_API_IMAGE_BASE_URL=https://api.example.com/images
NEXT_PUBLIC_SITE_URL=https://alfagrouptech.com
```

Set `NEXT_PUBLIC_ENABLE_PWA=false` (or omit it) to suspend PWA functionality;
see the kill-switch section above.

The API origins injected into the service worker are read at build time from
`NEXT_PUBLIC_API_BASE_URL`, `API_BASE_URL`, and
`NEXT_PUBLIC_API_IMAGE_BASE_URL`.

The included `next.config.mjs` sets:

- `/sw.js`: `Cache-Control: no-cache, no-store, must-revalidate`,
  `Service-Worker-Allowed: /`.
- `/manifest.webmanifest`: `application/manifest+json`.
- `/offline.html` and icons: appropriate cache headers.

If a CDN sits in front of the app, make sure `/sw.js` is not cached at the
edge. `/sw-policies.js` should also be revalidated.

Set `PWA_CACHE_VERSION` only if a deployment pipeline needs an explicit
human-controlled cache version. Otherwise the generated content hash is used.

## Verification

```bash
npm test                 # Jest unit/integration tests
npm run test:e2e:pwa     # production build + PWA Playwright tests
npm run pwa:check        # verifies public/sw.js is current
npm run pwa:generate     # regenerate the service worker manually
npm run pwa:assets       # regenerate icons/splash screens from the logo
```

`npm run test:e2e:pwa` automatically builds with `NEXT_PUBLIC_ENABLE_PWA=true`
so the enabled PWA behaviour is always covered. A normal build without that
variable remains PWA-disabled by default.

The Playwright suite starts a local mock API and a production Next.js server.
It verifies manifest/installability, service-worker scope and response headers,
offline reloads and in-app link navigation, private/admin cache exclusion,
public API caching through XHR (the axios browser adapter), auth and
transaction network-only behavior, update activation plus cache-version
cleanup, cross-tab update blocking via a real shared Web Lock, logout cache
cleanup, and install guidance.

The Jest suite additionally verifies cache policy hardening (redirects,
`Vary: Cookie/Authorization`, non-HTML navigation responses), update blocking
offline and during checkout, cross-tab checkout locks, stale lease expiry,
tab closure, Web Locks atomicity, BroadcastChannel/localStorage notification
fallback, session cleanup through `RequireAuth`, icon and manifest dimensions,
all linked iOS splash assets, and the favicon precache.

## Security notes and limitations

- Auth tokens remain in `localStorage` as before. They are never written to
  Cache Storage and never appear in service-worker cache keys.
- Private account pages and all admin pages are excluded from offline page
  caching.
- The authenticated cart is not mutated offline and is not queued for replay.
  A guest cart remains local by design and is labelled as such when offline.
  Checkout/order placement always requires a live server response; the UI
  never shows an offline success state.
- Search and filtering use POST requests and are therefore not cached. Their
  results may still be available from a previously cached page.
- Firefox desktop does not expose `beforeinstallprompt`; installation
  entry points are shown only when the browser advertises installability or
  for iOS Safari instructions.
- Lighthouse 13 no longer exposes a PWA category. Installability is verified
  through Chromium's CDP `Page.getInstallabilityErrors` in the E2E suite.
- Real iOS Safari/Android hardware installation and real-device push/standalone
  behaviour are not executed in this repository. The iOS checks use Playwright
  device emulation (Chromium engine) to validate the guidance UI and manifest.
- Cross-tab update activation is protected by Web Locks on browsers that
  support it. Browsers without Web Locks use expiring localStorage leases; that
  fallback is best-effort and may have a sub-second race window, but stale locks
  expire after 30 seconds. Checkout still requires a definitive server response.
- Live HTTPS, CDN edge cache behaviour, and the production domain must be
  verified after deployment. `/sw.js` must not be cached at the CDN edge.
- The existing homepage skeleton-to-content transition can produce layout
  shift on slow connections. This predates the PWA layer; a future improvement
  is to server-render the homepage product sections or reserve exact skeleton
  heights.
